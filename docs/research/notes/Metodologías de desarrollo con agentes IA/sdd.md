# Spec-Driven Development (SDD) for AI coding agents: methodology and implementations

Research date: 2026-10-27. Star counts were read from the GitHub repo pages on that date. Older information carries its own date.

## 1. What SDD is, who coined or popularized it, and what variants exist

### Takeaway
SDD means writing a structured, behavior-oriented natural-language spec before the agent writes code, and treating that spec as the shared source of truth. Sean Grove's 2025 talk "The New Code" (OpenAI) popularized it, and so did GitHub Spec Kit (Sept 2025) and AWS Kiro (July 2025). The term predates LLMs (an agile paper from 2004). Böckeler's taxonomy of spec-first, spec-anchored and spec-as-source is the accepted way to classify tools. The term is "semantically diffused" and poorly defined.

### Cited Findings
- Definition: a spec is written before AI coding and serves as the source of truth for both the human and the AI. A spec is "a structured, behavior-oriented artifact (or set of artifacts) written in natural language" that guides coding agents. Published 15 Oct 2025 by Birgitta Böckeler (Thoughtworks). — [martinfowler.com, Understanding SDD](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)
- Three levels. **Spec-first**: a spec written for the current task. **Spec-anchored**: the spec is kept after the task and used to evolve the feature. **Spec-as-source**: the spec is the main artifact and humans never edit code. All SDD is spec-first, but not all of it aims higher. — [martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)
- Distinction between the "memory bank" (rules files, product and codebase descriptions that apply to every session) and specs (which apply only to the tasks that create or change a feature). — [martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)
- Böckeler: "spec-driven development" is not well defined and already "semantically diffused"; some people use "spec" to mean "detailed prompt." — [martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)
- Early use of the term: Ostroff, Makalsky and Paige (2004), "Agile Specification-Driven Development" (XP 2004, LNCS 3092). It combined TDD with design by contract, treating tests and contracts as complementary specs. — [Wikipedia](https://en.wikipedia.org/wiki/Spec-driven_development); [DOI](https://doi.org/10.1007/978-3-540-24853-8_12)
- Wikipedia classes it as documentation-driven development, a relative of model-driven development and round-trip engineering. — [Wikipedia](https://en.wikipedia.org/wiki/Spec-driven_development)
- Sean Grove (OpenAI), "The New Code: Specifications as the Source of Truth" (2025, AI Engineer World's Fair). Prompts are thrown away while generated code is kept, which is like "shredding the source and version-controlling the binary." Written specs outlive any single model run. His example was OpenAI's Model Spec in Markdown, where clauses have IDs and example prompts act as tests. — [ai.engineer talk page](https://www.ai.engineer/talks/8rABwKRsec4-specifications-are-the-new-code); [HackerNoon summary](https://hackernoon.com/openais-new-code-could-make-spec-authors-the-new-rockstars-of-dev). (Sources disagree on the venue: most say AI Engineer World's Fair, one newsletter says DevDay — [buttondown](https://buttondown.com/snapsynapse/archive/issue-008).)
- GitHub framing ("power inversion"): "Specifications don't serve code—code serves specifications"; you maintain software by evolving specs and regenerating plans and code. — [spec-driven.md in github/spec-kit](https://github.com/github/spec-kit/blob/main/spec-driven.md)
- Den Delimarsky (GitHub): SDD makes technical decisions explicit, reviewable and evolvable (15 Sept 2025). — [Microsoft dev blog](https://developer.microsoft.com/blog/spec-driven-development-spec-kit/)
- Thoughtworks Radar (Nov 2025, Assess): workflows start from a structured functional spec broken into smaller pieces and tasks. The spec can be one document or several structured artifacts. — [Thoughtworks Radar](https://www.thoughtworks.com/radar/techniques/spec-driven-development)
- A defense of SDD's lineage argues that TDD is SDD at the unit level (Piskala, arXiv, submitted to AIWare 2026). Reported in search summaries; I did not open the paper. — [dbreunig, The Rise of SDD (Feb 2026)](https://www.dbreunig.com/2026/02/06/the-rise-of-spec-driven-development.html) (lineage context)

### Inferences
- The working definition in practice is a phased pipeline, roughly *(constitution/steering) → requirements/spec → design/plan → tasks → implement (→ verify/archive)*, with human review between phases. The tools differ mainly in three ways: (a) the level they aim for (first, anchored or source), (b) how heavy the artifacts are, and (c) whether specs persist and get merged back (OpenSpec archive, Spec Kit converge, Tessl spec-as-source).
- "Memory bank" or steering (persistent project context) and per-change specs are two separate layers in nearly every tool. That is a useful axis for comparing SDD with other agent methodologies.

### Gaps
- No single primary source shows who first used the phrase "spec-driven development" for LLM agents. Grove's talk and the Spec Kit and Kiro launches are what popularized it in 2025.

## 2. The implementations: phases, artifacts, commands, roles, gates, verification, memory

### Takeaway
Spec Kit (GitHub, about 143k stars, v1.0 on Aug 2026) is the reference toolkit: constitution plus specify/plan/tasks/implement, with extensions, presets and workflows. Kiro (AWS) is an IDE, CLI and web product with requirements, design and tasks, EARS requirements, steering files, and parallel task "waves." OpenSpec (about 73k stars) is the lightweight, brownfield, delta-based option. BMAD (about 55k stars) is persona/agile-team SDD. GSD (about 64k stars on the archived repo, now GSD Core) is context-engineering SDD with fresh subagents. Tessl began as spec-as-source but in 2026 pivoted to an "agent enablement / skills" platform.

### GitHub Spec Kit
- Initial commit 21 Aug 2025, by Den Delimarsky, who conceived it with John Lam. Announced 2 Sept 2025 on the GitHub Blog as an "experiment" that works with Copilot, Claude Code and Gemini CLI. MIT licensed. — [Spec Kit history](https://github.github.com/spec-kit/history.html); [GitHub Blog launch](https://github.blog/ai-and-ml/generative-ai/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit); [Visual Studio Magazine](https://visualstudiomagazine.com/Articles/2025/09/03/GitHub-Open-Sources-Kit-for-Spec-Driven-AI-Development.aspx)
- Timeline: Manfred Riem became lead maintainer on 22 Jan 2026. Extension system Feb 2026, presets Mar 2026, workflow engine Apr 2026, bundles Jun 2026. v0.9.5 (5 Jun 2026) added the `bug` extension, v0.13.0 (17 Jul 2026) the `assess` extension, and **v1.0.0 shipped 21 Aug 2026**. At 1.0 it had 38 agent integrations, 157 community extensions, 33 presets and 270+ contributors. — [Spec Kit history](https://github.github.com/spec-kit/history.html)
- Popularity: 143.4k stars and 12.8k forks (Oct 2026). — [github/spec-kit](https://github.com/github/spec-kit)
- Commands (current hyphenated form): `/speckit-constitution`, `/speckit-specify`, `/speckit-plan`, `/speckit-tasks`, `/speckit-implement`, `/speckit-converge`. Implement and converge repeat until converge reports "Converged." Bug extension: `/speckit-bug-assess` → `fix` → `test`, with a verdict of verified, partial or failed. Assess extension: intake → research → define → shape → decide, with a verdict of go, needs-clarification or kill. CLI: `specify init <proj> --integration copilot`, plus `specify extension|preset|workflow|bundle search`. Folders: `.specify/memory`, `.specify/bugs/<slug>/`, `.specify/assessments/<slug>/`. — [github/spec-kit](https://github.com/github/spec-kit). (The launch-era commands were `/specify`, `/plan`, `/tasks` — [GitHub Blog](https://github.blog/2025-09-02-spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/).)
- Artifacts: `memory/constitution.md` (immutable architectural principles), and per feature `spec.md` (what and why, no implementation), `plan.md` (tech choices traced to requirements), `research.md`, `data-model.md`, `contracts/`, `quickstart.md` (validation scenarios), `tasks.md` (tasks marked `[P]` can run in parallel). — [spec-driven.md](https://github.com/github/spec-kit/blob/main/spec-driven.md)
- Gates and template constraints: ambiguities must be written as `[NEEDS CLARIFICATION: …]`, and a spec is incomplete while any remain. Checklists act as "unit tests" for the spec. Speculative "might need" features are banned. Constitution articles: I Library-First, II CLI Interface (JSON output), III Test-First ("NON-NEGOTIABLE"; tests are approved and must fail before code), VII Simplicity (≤3 projects), VIII Anti-Abstraction, IX Integration-First (real DBs over mocks, contract tests first). "Phase -1 gates" check VII, VIII and IX before planning. A failed gate needs a justification in a "Complexity Tracking" section. Tests are written in the order contract → integration → e2e → unit, before source. — [spec-driven.md](https://github.com/github/spec-kit/blob/main/spec-driven.md)
- In Böckeler's test, one feature produced about 8 files (spec, plan, tasks, research, data-model, api, component…). Each spec gets its own branch, so in practice a spec is tied to a change request (spec-first, though GitHub's messaging is spec-anchored). Checklists work as a "definition of done," but the AI interprets them. — [martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)
- Verification: the README recommends reviewing each step's output. The automated signals are the converge loop and the bug-extension verdict. — [github/spec-kit](https://github.com/github/spec-kit)

### AWS Kiro
- Announced 14 Jul 2025. Sources disagree on the GA date: 17 Nov 2025 (alongside Kiro CLI) is the most repeated, but May 2026 and March 2026 also appear. Pricing: Free (50 credits), Pro $20 (1,000), Pro+ $40, Pro Max $100, Power $200; extra credits $0.04. — [rywalker.com](https://rywalker.com/research/kiro); [tooldirectory.ai](https://tooldirectory.ai/tools/kiro); [usagepricing](https://www.usagepricing.com/blueprint/kiro) (secondary sources; not checked against AWS)
- Workflow (docs updated 15 Oct 2026): Requirements (or Bug Analysis) → Design → Tasks. Files: `requirements.md` (user stories plus acceptance criteria), `bugfix.md` (current, expected and *unchanged* behavior), `design.md` (architecture, sequence diagrams, data flow, error handling, testing strategy), `tasks.md`. Spec types: Feature (Requirements-First or Design-First variants), Bugfix (root cause, fix design, regression checks), and **Quick Spec** (all three artifacts in one pass with no approval gates). "Analyze Requirements" flags inconsistencies and gaps before design. "Correctness" uses property-based testing (IDE only). "Run all tasks" builds a dependency graph and runs independent tasks in parallel "waves." Available in IDE, CLI and Web. — [kiro.dev/docs/specs](https://kiro.dev/docs/specs/)
- Requirements use EARS notation (Easy Approach to Requirements Syntax). Steering files live in `.kiro/steering/`. Agent hooks fire on repository events. — [gilricardo.com review](https://www.gilricardo.com/blog/kiro-review-spec-driven-agentic-ide); [rywalker.com](https://rywalker.com/research/kiro)
- Böckeler (Oct 2025): Kiro is mostly spec-first. Acceptance criteria use GIVEN/WHEN/THEN (she describes them that way). Tasks trace back to requirement numbers, and the UI runs and reviews one task at a time. Default steering files are `product.md`, `structure.md`, `tech.md`. — [martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)

### OpenSpec (Fission-AI)
- 73.2k stars, 5.0k forks, about 1,009 commits, MIT (Oct 2026). Claims support for 30+ assistants. Install via a curl/PowerShell binary, npm (Node 20.19+), or Homebrew. — [Fission-AI/OpenSpec](https://github.com/Fission-AI/OpenSpec)
- Default commands: `/opsx:explore` (thinking partner, no code), `/opsx:propose <name>`, `/opsx:apply`, `/opsx:archive`. Expanded profile: `/opsx:new`, `/opsx:continue`, `/opsx:ff` (fast-forward), `/opsx:verify`, `/opsx:bulk-archive`, `/opsx:onboard`. — [OpenSpec](https://github.com/Fission-AI/OpenSpec)
- Artifacts: the current truth lives in `openspec/specs/`. Each change has `openspec/changes/<name>/` with `proposal.md` (why and what), `specs/` (spec **deltas**, e.g. `## ADDED Requirements` with Requirement/Scenario WHEN/THEN blocks), `design.md`, `tasks.md`. Archiving moves the change to `openspec/changes/archive/<date>-<name>/` and merges the deltas into `openspec/specs/`. That merge is how OpenSpec becomes spec-anchored. — [OpenSpec](https://github.com/Fission-AI/OpenSpec)
- Philosophy: "fluid not rigid, iterative not waterfall," built for brownfield. It calls Spec Kit "thorough but heavyweight" (rigid phase gates, lots of Markdown, Python setup) and Kiro powerful but locked to its own IDE. A beta "Stores" feature plans in a separate shared repo. — [OpenSpec](https://github.com/Fission-AI/OpenSpec)

### BMAD-METHOD (bmad-code-org)
- 54.6k stars, 6.1k forks. v6.12 is stable (`npx bmad-method install`, then `bmad-build` and `bmad-help`). v7 is in alpha on main, distributed as Agent Skills (`npx skills add bmad-code-org/BMAD-METHOD --skill '*'`) and through the Claude Code and Codex plugin marketplaces, with a stated ETA of 16 Oct 2026 (I could not confirm it shipped). — [BMAD-METHOD](https://github.com/bmad-code-org/BMAD-METHOD)
- Current README: scale-adaptive (small changes go straight to build). The loop is Clarify → Plan → Build and verify → Learn and adjust. "Durable context" carries product and technical decisions across chats. Modules: BMad Method, BMad Builder, Creative Intelligence Suite, Test Architect, BMad Loop (unattended epic builds), Game Dev Studio. — [BMAD-METHOD](https://github.com/bmad-code-org/BMAD-METHOD)
- Roles and artifacts (secondary sources): planning agents Analyst, PM and Architect produce the PRD and architecture docs. Implementation runs on **story files**, a "context-packing device" that puts everything one dev agent needs into one file. Sources disagree on the phase count (four phases vs upstream/downstream). — [augmentcode BMAD guide](https://www.augmentcode.com/guides/bmad-method-ai-development); [codemyspec BMAD explained](https://codemyspec.com/blog/bmad-method-explained)

### GSD ("Get Shit Done")
- Original repo `gsd-build/get-shit-done`: 64.2k stars, created by "TÂCHES," described as a "lightweight meta-prompting, context engineering and spec-driven development system for Claude Code." **Archived 26 Jun 2026**; development moved to GSD Core. — [gsd-build/get-shit-done](https://github.com/gsd-build/get-shit-done)
- GSD Core (`open-gsd/gsd-core`): 10.9k stars, v1.7.0, MIT. Per-phase loop Discuss → Plan → Execute → Verify → Ship, repeated for each milestone. Commands: `/gsd-new-project` (greenfield), `/gsd-onboard` (existing code); install with `npx @opengsd/gsd-core@latest`. Context-rot handling: research, planning and execution run in fresh-context subagents, and plans run in parallel waves where each executor starts with a clean 200k context. `STATE.md` and `CONTEXT.md` persist across sessions. Verify walks through what was built, diagnoses problems, and writes fix plans before a phase is done. Ship opens the PR and archives the phase. Runtimes: Claude Code, OpenCode, Codex, Copilot, Cursor, Windsurf, Kimi, Kilo, Antigravity and others. — [open-gsd/gsd-core](https://github.com/open-gsd/gsd-core)

### Tessl
- In Oct 2025 Böckeler found it the only tool explicitly aiming for spec-anchored, and it was exploring spec-as-source. It was a CLI and MCP server, with one spec mapped to one code file, generated files headed `// GENERATED FROM SPEC - DO NOT EDIT`, and `@generate`/`@test` tags and an API section in specs. `tessl build` generates code; `tessl document --code` reverse-engineers a spec from code. Memory lived in `.tessl/framework`, `KNOWLEDGE.md` and `AGENTS.md`. Regenerating from the same spec gave different code. — [martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)
- Thoughtworks (Nov 2025): Tessl Framework was in private beta as of Sept 2025. — [Thoughtworks Radar](https://www.thoughtworks.com/radar/techniques/spec-driven-development)
- 2026 pivot: tessl.io now calls itself "the agent enablement platform" ("Build your software factory, one skill at a time") built on Skills, Loops and a Factory, plus Tessl Registry (scanned and scored skills). The homepage never mentions specs or spec-as-source. — [tessl.io](https://tessl.io). The docs still say the full framework is in closed beta — [docs.tessl.io](https://docs.tessl.io/common-workflows/existing-code-to-spec). A secondary source says the Spec Registry entered open beta in Sept 2025 and the focus moved from specs to skills in early 2026 — [issoh.co.jp](https://www.issoh.co.jp/tech/details/11690/)

### Agent OS (Builder Methods, Brian Casel)
- A free, open-source system for defining and managing coding standards for Claude Code, Cursor and Windsurf. v3 workflow: Install → Discover (standards from the codebase) → Inject → Shape. Shaping questions run in Claude Code **plan mode** to produce specs aligned with standards and the product mission. Outputs go in an `agent-os/` directory. — [buildermethods.com/agent-os](https://buildermethods.com/agent-os)

### Others (one line each)
- **cc-sdd (gotalab)**: npx tool that brings Kiro's requirements → design → tasks → implement flow, with Kiro-compatible specs, to Claude Code, Codex, Cursor, Copilot, Gemini CLI and Windsurf. v3.0 is reworked around Agent Skills and long-running autonomous implementation. — [cc-sdd README](https://cdn.jsdelivr.net/gh/gotalab/cc-sdd@main/README.md); [Gigazine](https://www.gigazine.net/gsc_news/en/20251108-cc-sdd)
- **Traycer**: a spec and plan layer that hands each phase to a chosen coding agent, then **verifies** the implementation against the plan with comments ranked Critical, Major, Minor or Outdated. In phases/YOLO mode it chains handoff → verify → next phase. — [Traycer verification docs](https://docs.traycer.ai/tasks/verification); [Traycer YOLO mode](https://docs.traycer.ai/tasks/yolo-mode)
- **AI-DLC (AWS)**: positioned as a full methodology that implements SDD. — [buildwithdc substack](https://buildwithdc.substack.com/p/aidlc-implements-spec-driven-development)

### Inferences
- **Verification is the weakest part of most tools.** Spec Kit relies on human review plus converge, Kiro adds property-based testing, OpenSpec has an optional `/verify`, Traycer makes plan-vs-diff verification its main feature, and GSD has an explicit Verify phase. Most rely on the AI reading checklists, which Böckeler notes is not guaranteed compliance.
- **Ideas worth borrowing.** Spec Kit's `[NEEDS CLARIFICATION]` markers and constitution "Phase -1 gates" with a required Complexity Tracking justification. Kiro's Quick Spec (a size-adaptive path with no gates) and bugfix "unchanged behavior" section. OpenSpec's delta specs, with archive merging them into a living spec (anchoring without regeneration). GSD's fresh-context subagents and wave execution. BMAD's story file as a self-contained context package. Traycer's severity-ranked plan-conformance review.
- **The trend in 2026 is toward size adaptivity** (Kiro Quick Spec, BMAD scale-adaptive, Spec Kit bug and assess extensions) **and toward skills/plugins as the distribution format** (BMAD v7, cc-sdd v3, Tessl pivot). That responds directly to the overhead critique.

- I did not retrieve the full current command lists for GSD Core (docs/COMMANDS.md), BMAD v6 personas (official), or Agent OS v3 commands and folders. The commonly cited GSD artifacts (PROJECT.md, REQUIREMENTS.md, ROADMAP.md, PLAN.md, SUMMARY.md) and the BMAD Scrum Master/QA roles are not confirmed by a primary source here.
- Spec Kit's `clarify`, `analyze` and `checklist` commands (from late-2025 versions) did not appear on the current README I fetched, so their status in v1.x is unverified.
- Cursor's and Windsurf's native spec/plan features: the search returned nothing usable.

## 4. Critiques and known weaknesses

### Takeaway
The critiques agree on five points. A single heavy workflow does not fit every task size. Reviewing verbose Markdown is worse than reviewing code. Agents ignore specs anyway, which gives a false sense of control. Specs drift and go stale. And up-front specs deny the learning that happens during implementation (Beck and Fowler), which risks waterfall or a repeat of MDD. Thoughtworks kept SDD at "Assess," and the blip has since dropped off the Radar.

### Cited Findings
- Thoughtworks Radar (5 Nov 2025, **Assess**): workflows are "elaborate and opinionated," behavior varies with task size, some tools produce long spec files that are hard to review, the audience for PRDs and user stories is unclear, and the field may be relearning the "bitter lesson" that hand-written rules for AI don't scale. The blip is not in the current Radar edition. — [Thoughtworks Radar](https://www.thoughtworks.com/radar/techniques/spec-driven-development)
- Böckeler (Oct 2025). Kiro turned a small bug fix into 4 user stories with 16 acceptance criteria. Spec Kit was overkill for a medium feature, and plain AI-assisted coding would have given more control in the same time. Spec Kit's files were repetitive and tedious to review ("I'd rather review code"). Agents ignored instructions or over-applied the constitution, and re-generated existing classes as duplicates. It was hard to know when to stay functional and when to go technical. The target user was unclear. Spec-as-source risks combining MDD's rigidity with LLM non-determinism ("Verschlimmbesserung"). — [martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)
- Kent Beck, via Fowler (8 Jan 2026): SDD descriptions stress writing the whole spec before implementation, which "assumes you won't learn anything during implementation." Fowler agrees that the experimentation loop builds the mental model a spec needs. — [Fowler Fragments 2026-01-08](https://martinfowler.com/fragments/2026-01-08.html)
- Gojko Adzic warned that SDD could bring back the rigidity agile tried to escape (Sept 2025). — [Visual Studio Magazine](https://visualstudiomagazine.com/articles/2025/09/16/github-spec-kit-experiment-a-lot-of-questions.aspx?p=1)
- "SDD is waterfall": practiced badly (frozen specs handed off), it reproduces waterfall's failure modes. — [Augment Code, SDD vs Waterfall](https://www.augmentcode.com/guides/spec-driven-development-vs-waterfall)
- Drift: the most common practical complaint is that the spec quietly stops being true, and a stale spec can be worse than none because people trust it. Overhead is usually not worth it for a solo developer or a prototype. — [dev.to SDD in 2026](https://dev.to/krlz/spec-driven-development-in-2026-what-it-is-the-tooling-and-how-teams-actually-use-it-2fk2); [CODERCOPS guide](https://blog.codercops.com/blog/spec-driven-development-guide-2026) (practitioner blogs)
- Hype skepticism about "executable specs." — [Medium, The Emperor's New Code](https://medium.com/@delimiterbob/the-emperors-new-code-hype-vs-reality-of-ai-executable-specs-ff64d961e8ab)
- Competitor critique: OpenSpec calls Spec Kit heavyweight, with rigid gates and too much Markdown. — [OpenSpec](https://github.com/Fission-AI/OpenSpec)

### Inferences
- When SDD fails: small or unclear tasks, exploratory work where the spec must be learned, brownfield code the spec doesn't capture (duplication), and teams with no owner keeping specs current. When it fits: medium-to-large well-understood features, multi-agent or parallel execution needing a shared contract, and audit and handoff needs.
- The answers to the critiques visible in 2026 tooling: size-adaptive paths (Kiro Quick Spec, BMAD), delta specs merged on archive (OpenSpec), automated conformance verification (Traycer, Spec Kit converge, GSD Verify), and fresh-context execution (GSD). A methodology comparison should check how each addresses drift, review burden and sizing.

### Gaps
- No controlled empirical study comparing SDD with plain agentic coding on quality or cost was found. The evidence is anecdotal or vendor-sourced.
- Hacker News threads were not retrieved in this pass.
- Thoughtworks' current (post-Nov 2025) position is unknown beyond the blip having dropped off the current edition.
