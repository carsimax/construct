# Memory maintenance

Objective: less noise in relations and prompts, a read signal on memories, a list of passive rows to clean up, and the four follow-ups of the memory MCP review. Branch: feat/memory-maintenance. Baseline: ae23af7. Delivery strategy: single-pr. Test runner: `node --test tests/`.

## Specs

- **S1 — Passive rows are never relation candidates.** "excluir las filas `passive` de los candidatos a relación". `candidatesFor` in memory-store.mjs skips rows whose type is `passive`; a save whose only title matches are passive rows prints no candidates and records no relation. Existing pending relations are left alone.
- **S2 — More harness notices are not stored as prompts.** "ampliar el filtro de prompts del harness: siguen llegando `GENTLE_AI_REVIEW_BINDING`, `Current todo list:` y `The todo plan has not been reviewed`". `SKIPPED_PROMPT` in memory-hooks.mjs also skips prompts that start (after leading whitespace) with `GENTLE_AI_REVIEW_BINDING `, `Current todo list:`, `The todo plan has not been reviewed`, or `Stop hook feedback:`. A prompt that only mentions one of these later in its text is still stored.
- **S3 — Reads are counted.** "contador de accesos". Two observation columns, `access_count INTEGER NOT NULL DEFAULT 0` and `last_accessed_at TEXT`, added by `init` with `ALTER TABLE ... ADD COLUMN` when missing, in the same `BEGIN IMMEDIATE` transaction, without changing `user_version` (SCHEMA_VERSION stays 1), so an older construct on another worktree of the same clone still opens the store. A concurrent init that finds the column already added is not an error. The fresh-database `SCHEMA` declares both columns. `get <id>` on a live row (CLI and so `mem_get_observation`) adds 1 and sets `last_accessed_at`; `search`, `context`, `timeline`, and a missing or deleted id do not count. `get` prints `accessed: N` (after this read). In search ranking, `access_count` joins `revision_count + duplicate_count` in the existing small reuse boost. `doctor` passes on a store with the columns and on one without them (before the next init adds them). Export and import keep their current fields (no new export field).
- **S4 — A cleanup list of passive rows.** "consolidar en bloque las filas `passive`". New read-only `construct-memory review passive [--days N] [--json]`: live `passive` rows never read (`access_count = 0`) whose `created_at` is at least N days old (default 30, N a positive integer, else the error `review passive --days needs a positive whole number`), oldest first, one line each in the `hit` format, or `no passive rows to review`. It writes nothing; the agent then uses `consolidate` or `delete` as today. install.sh pre-approves it like `review stale`. The memory skill (800-word cap) names it in the Consolidate and review section.
- **S5 — The MCP timeout path is tested.** Review follow-up "the 10 s timeout path is untested". `memory-mcp.mjs` reads its timeout from `CONSTRUCT_MEMORY_MCP_TIMEOUT_MS` when it is a positive integer (a test hook, named in a comment, not documented as a user option), else 10000. A test points `CLAUDE_PLUGIN_ROOT` at a scratch plugin whose `bin/construct-memory` hangs and gets `isError: true` with `construct-memory timed out`, and the server keeps answering later requests.
- **S6 — Output past the buffer says so.** Review follow-up "output past `maxBuffer` reports a generic error". When the CLI output exceeds the 16 MiB buffer, the result is `isError: true` with `construct-memory output exceeded 16 MiB`. Tested with a scratch CLI that prints more than that.
- **S7 — One failed reply never stops the queue.** Review follow-up "a rejected promise in the line queue would stop later replies". The line queue catches a rejection so later lines are still handled.
